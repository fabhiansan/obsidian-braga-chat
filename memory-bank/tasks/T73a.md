## Description

Give the canonical Chat component map an explicit, code-agnostic repository
model and visual guide. State the general resource behaviors independently of
any one data source, then show how the current Obsidian AI chat maps those
behaviors to its vault integration. Add ASCII mockups of the main responsive
chat surfaces so a builder can understand which controls and states the
component needs to represent.

This is a bounded baseline update under T73. Future feature and source
reconciliation remains with the ongoing parent task.

## Acceptance Criteria

- [x] Define chat-level repository/resource concepts and capability families,
  including search/browse, references, query, read, create, update,
  delete/archive, organization/relationships, and bounded context/attachments.
- [x] Clarify that these are optional capabilities subject to repository
  permissions, validation, audit/version rules, and domain constraints.
- [x] Explicitly classify resource references, current-resource context,
  groupings, and tags as general interaction concepts; identify Obsidian
  syntax and APIs as adapter-specific realizations.
- [x] Crosswalk the general repository capability families to current Obsidian
  AI tools and UI affordances without treating their names as universal APIs.
- [x] Add repository-independent ASCII mockups for wide and narrow workspaces,
  resource/model/participant pickers, history/search and overflow, tool
  approval/progress, message selection/export, and optional sync/collaboration.
- [x] Keep unavailable repository operations and optional services visibly
  conditional in both the prose and mockups.
- [x] Add separate mobile image mockups with external callout labels for
  message anatomy, single-chat layout, and multi-tab chat; show user and agent
  timestamps, tokens, actions, provider/model identity, response duration, and
  active generation status.

## Implementation Details

The canonical map now separates the general capability model from the current
Obsidian AI tool catalog and provides a crosswalk between them. The wireframes
describe required information and interaction surfaces, not a prescribed
visual design. Provider profiles and chat-session storage remain separate from
the data-repository adapter.
