## Description

Maintain the canonical, code-agnostic map of the Obsidian AI Chat component so
that an agent or developer can use it to reproduce every chat capability in
any language or framework. The map covers the Chat UI, user-visible behavior,
tool surface, conversation lifecycle and state, and the backend services that
support those behaviors. It excludes plugin features unrelated to chat.

This is an ongoing knowledge-maintenance task. It owns keeping the map
complete, accurate, and linked to the Memory Bank's feature records as chat
capabilities evolve. It does not own implementation of the individual
features.

## Acceptance Criteria

- [ ] Keep `implementation-details/chat-component-capability-map.md` as the
  single canonical cross-layer map and keep it discoverable from the Memory
  Bank entry points.
- [ ] Reconcile the map against current observable chat behavior, the
  implementation notes, and relevant completed, active, and planned chat task
  records; record coverage gaps rather than silently omitting them.
- [ ] For each capability, describe what the user can do and observe, the
  resulting conversation or UI state, required services, availability
  conditions, and known limits or failure behavior where relevant.
- [ ] Label capabilities accurately as available, optional, host/provider
  dependent, planned, or unverified; do not imply that unverified or planned
  behavior is shipped.
- [x] Distinguish repository-neutral resource interactions and capability
  families from adapter-specific syntax and APIs, with a crosswalk to the
  current Obsidian implementation.
- [x] Provide repository-independent ASCII mockups for the main responsive
  workspace and the major chat pickers, history, tool, selection, and optional
  collaboration surfaces.
- [ ] Keep descriptions independent of programming language and framework,
  and omit plugin features with no direct chat behavior.
- [ ] Update the map when a directly chat-related feature changes, and record
  meaningful coverage reconciliations in this task and the Memory Bank edit
  history.

## Implementation Details

Use the visible Chat experience and current Memory Bank/source evidence as the
basis for the map. Organize information around capabilities and observable
contracts rather than source files or class names. Keep implementation-specific
references only as evidence links, not as requirements for a replacement.
When capability status or acceptance evidence is uncertain, state that
uncertainty explicitly and link the relevant task record.

Keep the scope to the chat component and services it invokes directly. For
example, document vault access only where chat uses it for context, attachments,
note actions, or tools; do not absorb unrelated settings, sync, release, or
plugin administration behavior.
